# ConveneCore: isolated organization workspaces
## Boundary
Database-per-organization and dedicated application stack, rather than shared-table tenant IDs. Every managed tenant uses its own Compose project, PostgreSQL database/role/credentials, Redis instance and queue, backend process, worker, frontend, private network and storage volume. Local primary keys can overlap without sharing data. Organization administrators are local administrators, not platform operators. Public blank templates are identical code, not shared private records. Account emails can repeat across organizations. Tenant selection is the organization's HTTPS hostname; invitation URLs and JWT issuer are tenant-specific. The operator's reverse proxy must reject unknown hostnames and never default to a tenant. The frontend alone is published to a loopback port. Do not expose PostgreSQL, Redis or backend ports.
## Provisioning
Use a Linux host with Docker Compose v2, a trusted reverse proxy and per-host TLS certificates. From the release checkout:
    sudo python3 deploy/tenantctl.py provision alpha --host alpha.example.com --admin-email admin@alpha.example.com --port 19081
    sudo python3 deploy/tenantctl.py start alpha
    sudo python3 deploy/tenantctl.py render-nginx
Install the generated Nginx configuration into the existing operator-managed proxy after issuing certificates. Configure a dedicated default server that rejects unknown HTTP hosts and TLS handshakes; do not replace unrelated applications' reverse-proxy configuration. Validate with nginx -t before reload. Never publish loopback ports through a public firewall or a second proxy. The registry and tenant.env files must be operator-only. Deliver the generated bootstrap password securely, change it after login, and set optional tenant-specific Gemini/SMTP credentials in that tenant's environment file before restarting. No shared tenant credentials or database volumes.
Use list/status for operations and suspend to stop a workspace without deleting data. Re-render/reload proxy after changes. There is no destructive delete command. This is an operator control plane, not a self-service SaaS signup or billing portal.
## Existing production data
Keep the original deployment unchanged until migration is rehearsed. Back up its database and entire recording/export/branding volume, verify restoration into a new isolated workspace, and preserve file paths within the container. Do not copy the old credentials or expose the existing workspace to a second organization. Rotate signing keys and require re-login. Check invitations, recording playback, structured minutes, backups, and mail. Cut over only after validation. Rollback by restoring the old proxy route and stopping the new stack; do not write to both copies. No automatic migration or production deployment is performed by this change.
## Verification
Run deploy/test_tenantctl.py and backend tests. Before any production activation, deploy two disposable organizations on a staging host, intentionally create overlapping IDs and emails, and verify both API and file access: login token replay, list/read/write/delete meetings, staff, private formats, transcript, minutes, invitations, live room, recordings, exports, settings, audit, backup and worker jobs. Confirm separate Docker network/volumes and no unknown-host route. Test same-site cross-origin mutations. Tenant infrastructure isolation does not protect against a compromised host operator or shared external AI/mail provider; configure provider contracts and retention accordingly.

## Fail-closed identity markers
Managed API startup and worker jobs check both database and storage identity markers. The first startup claims only an empty database and empty storage; an existing unlabelled deployment must be migrated offline by a trusted operator after verifying its ownership. Do not change a marker to attach a database to a different customer. For a rehearsed existing-data migration, restore into the already initialized dedicated workspace offline and ensure the restored database contains the correct marker in system_settings and the restored storage retains the corresponding .convenecore-tenant file. Verify before starting workers. Run deploy/smoke_isolation.py only on two disposable, freshly provisioned workspaces with the same initial admin email; it modifies and deletes test records and changes bootstrap passwords. It is not a production smoke test.

## Continuous verification
The pull-request CI job two-organization-isolation provisions two disposable stacks on an ephemeral GitHub runner. It checks Docker network and volume separation and then runs the API smoke suite, including recorded file contents, document XML, live-room session keys, JWT replay, settings, backup access and independent mutations. It removes the disposable volumes in an always-run cleanup step. No production credentials or production host access are used. Do not treat a queued or skipped check as a successful test. TLS certificate routing, real AI provider traffic, and migration of existing data require separate staging verification.
